## 1. What is being decided

#418 reproduced a completed record WRITE whose change a later firmware
acknowledgement retired, leaving flash older than the live image with
`(backed, dirty, stale) = (1, 0, 0)`. #419 asks for the contract that makes an
acknowledgement identify an image, before any production edit is scheduled.

This document decides four things and refuses to decide a fifth:

1. **Where the ownership boundary is**, across the donor producer, the parent
   backend, the firmware writer and the media (section 3).
2. **The contract**, as edge-level next-state rules on the existing interfaces
   plus two strobe bits and four status bits (section 4).
3. **Which alternatives are rejected and why** (section 5).
4. **What the evidence does and does not establish** (sections 6, 8 and 9).

It does not decide the product policy in section 10, which is the only part
that changes an owner-visible loss behaviour.

## 2. The two failures the contract has to answer

Both are reproduced in this proposal's co-simulation against the tracked
backend RTL and the tracked firmware translation unit (section 6).

### 2.1 An acknowledgement carries no image identity

`KL_nvm_backend.sv:485-488` is `dirty_n_w = dirty_set_w ? 1 : commit_ack_w ? 0
: dirty_r`. That is a correct per-cycle formula and it is faithful to the
design page's section 9.2. What it cannot express is which image the
acknowledgement covers, because nothing in the transaction carries one. The
unit bench measures the shape of that exactly, at the device face, on the
tracked module:

| edges between the WRITE completion and the acknowledgement | tracked module | proposed |
|---|---|---|
| 0 | change kept | change kept |
| 1, 2, 4, 8, 64 | **change retired** | change kept |

The protection that exists is one clock cycle wide. Everything outside it is
the defect, and the firmware's own commit spans milliseconds.

### 2.2 A blanked span can be promoted as a new saved state

This is the failure the brief names and it is not the same defect. The donor's
logical record write is two device commands, `ERASE_REGION` then `WRITE`
(`protocol-processor/hdl/packet_engine/KL_pp_nvm_port.sv:354-372`). Between
them the record's span is `0xFF`, and:

- the backend's `dev_busy_o` is **low**, so the firmware's single
  `NVM_RD_DEV_BUSY` test at `milan_baremetal.c:894` passes;
- `write_commit_w = done_r & was_write_r` at `:583` marks only WRITE, so the
  completed ERASE does not even mark the image dirty;
- an all-`0xFF` span at the position of the next required record is a **legal
  KLJ2 encoding** (design page section 6.1, the ratified erased-record rule),
  so `nvm_validate` returns `VD_OK`, the seal closes, the read-back verifies
  and the acknowledgement is accepted.

The result is a newest slot, at a higher sequence, whose record reads as never
written. A power cycle then restores the vendor default for a value a
controller had set. No CRC catches it, because the image is internally
consistent. Content alone cannot tell that span from a legitimate first boot,
which is why the answer has to be structural rather than a content rule.

Measured, baseline build, case `gap-before-window`, with a saved image already
in both slots:

```text
Milan NVM: slot A VD_OK seq 2, slot B VD_OK seq 1; offered A seq 2 (VD_OK)
Milan NVM: commit (dirty) seq 3 -> slot B, 2696 B, acknowledged.
```

Slot B, sequence 3, is now authoritative and its record `0x20` is erased.
`dirty` reads 0. The same happens when the WRITE fails and the producer gives
up (`failed-write`), where the blank is permanent rather than transient.

## 3. The ownership contract, settled

**The minimal repair is entirely inside this repository. #419 opens no donor
interface dependency.** That is the substantive finding of this section, and
it is the opposite of what an interface-first reading of the issue suggests.

The parent backend terminates the donor's device face. Every byte of the image
changes through that face, so the parent already observes every mutation and
every blanked span, with no new signal from anywhere:

| Fact the contract needs | Where the parent already has it |
|---|---|
| a record's bytes changed | `done_r & was_write_r` (`KL_nvm_backend.sv:583`) |
| a record's span was blanked | a completed `OP_ERASE_C`, which the module grants and terminates itself |
| an operation is in flight | `dev_busy_o` (`:753`) |
| which record | `dev_region_i`, latched at grant |

`protocol_processor_top.sv:2326`'s internal `nvm_busy_w` (the port's own busy,
which does span the whole logical operation, `KL_pp_nvm_port.sv:343`) is
**not needed** and is **not sufficient**:

- not needed, because parent-side `dev_busy | gap_open` already covers exactly
  the interval in which the image is not a completed-record state, and covers
  it for any initiator rather than for one;
- not sufficient, because it says nothing about a change the manager has
  captured and is still debouncing (`KL_acmp_nvm_shadow.sv`, `DEB_TICKS_P`),
  which is the residual in section 9.4.

So the ownership split is:

| Concern | Owner | Cross-repository? |
|---|---|---|
| Producing record bytes, framing, retry, debounce | donor manager and port | donor, unchanged |
| The logical operation's shape (ERASE then WRITE) | donor port | donor, unchanged |
| Detecting image mutation and blanked spans | **parent backend** | no |
| Capture window identity and acknowledgement admissibility | **parent backend** | no |
| Where the window is opened and released | **parent firmware** | no |
| Media, A/B promotion, container verdicts | parent firmware | no, unchanged |
| Accounting for a change captured but not yet written | donor | **optional**, section 9.4 |

Donor #14 and donor PR #26 are untouched by this proposal. No pin moves.

## 4. The proposed contract

Name: **the capture window**. An acknowledgement retires the dirty state only
if the backend can see that the image did not move between the point the
firmware started reading it and the point it acknowledged, and only if the
image was a completed-record state when that point was taken.

### 4.1 The rules

```
write_commit = done & was_write            (unchanged, :583)
erase_commit = done & was_erase
mut       = change_i | write_commit | erase_commit
gap       = gap_open | gap_stuck
cap_block = dev_busy | gap
arm       = control word 4, bit [3]
release   = control word 4, bit [4]
ack       = control word 4, bit [1]      (unchanged)

cap_armed' = arm ? 1 : (ack | release) ? 0 : cap_armed
cap_valid' = arm ? (~cap_block & ~mut) : (cap_valid & ~mut)
ack_ok     = ack & cap_armed & cap_valid & ~mut
ack_ref'   = arm ? 0 : (ack & ~ack_ok) ? 1 : ack_ref
dirty'     = mut ? 1 : ack_ok ? 0 : dirty

gap_open'   = erase_commit ? 1
            : (write_commit & gap_open & (op_region == gap_region)) ? 0
            : gap_open
gap_region' = erase_commit ? op_region : gap_region
gap_stuck'  = (erase_commit & gap_open & (gap_region != op_region)) ? 1 : gap_stuck
```

Reset clears all of them. `commit_busy` clears on `ack | release` as well as
on the existing deadline. `was_write` keeps its existing meaning exactly, so
the dirty semantics of a discarded write are unchanged; `was_erase` is latched
at grant only when the operation will actually blank bytes, which is when the
image is configured, the span is legal and its length is not zero. The refusal
and discard arms of the byte pump therefore open no gap, because they touch no
image.

### 4.2 The edges, and the priorities on each

| Edge | Meaning | Priority chosen, and why |
|---|---|---|
| `arm` | request a capture | `cap_valid` is set only when the image is a completed-record state and this edge is not itself a mutation. An arm is never deferred and never blocks a producer: it is granted or refused in one cycle. |
| `arm` with `cap_block` | refused capture | Published as `cap_valid = 0` rather than as a failed write, so the firmware reads one word and knows. |
| `mut` inside the window | the image moved | Wins over everything. This is the whole repair: the existing same-edge priority is generalised from one cycle to the window. |
| `ack` with `cap_valid` | retire | Clears `dirty`. Also closes the window, so the next attempt must arm again. |
| `ack` without a window, or repeated | refuse | Retires nothing, sets `ack_ref`. A repeated acknowledgement therefore cannot retire work that arrived after the first one. |
| `ack` on the same edge as `mut` | refuse | `dirty` was already protected by the existing priority; what is new is that `ack_ref` reports it, so the firmware does not believe the commit covered the change. |
| `release` | abandon | Closes the window and the commit bracket, retires nothing. Without it a failed commit blocks the retry for the whole 8,000 ms deadline and then revokes a durability claim no writer lost. |
| a completed ERASE | blank a span | Marks the image dirty (it did change) and opens the gap. |
| a completed WRITE to the gap region | close the span | Clears the gap. |
| a second ERASE while a gap is open | beyond the tracker | `gap_stuck`, cleared only by reset. Unreachable while the initiator keeps one operation outstanding (the port's F02.8 rule); fail safe rather than a guess if it ever is not. |

Three consequences of that table are worth stating as sentences, because they
are the choices the issue asks for by name.

**Arbitration: there is none, and that is the choice.** A logical operation
that has been granted always runs to completion. A producer request is never
deferred, queued or refused. The capture is what yields, every time, and the
only cost of yielding is a retried commit that `nvm_dirty` correctly reports
as outstanding meanwhile.

**The capture needs no timeout, because it holds nothing.** An abandoned
window is one flip-flop left set; it blocks no producer, holds no memory and
consumes no bandwidth, and the next attempt's arm overwrites it. The release
strobe exists for the **commit bracket**, which does hold something (the
8,000 ms deadline and the service loop's early return), not for the window.
The bracket keeps its existing deadline as the backstop for a firmware that
stops answering altogether.

**First boot is preserved by construction.** A record the processor has never
written since the media was blank has no open gap, because no ERASE ever
completed for it. The arm succeeds and its erased span is committed exactly as
the ratified erased-record rule requires. In the `no-change` case the
acknowledged container holds 45 erased records and one framed one, and the
repository's own decoder returns `VD_OK` for it. What the gap interlock
refuses is only a span that an ERASE blanked and no WRITE has closed, which is
a different thing that happens to look identical in the bytes.

### 4.3 Where the firmware opens and closes the window

The window has to open **before the seal**, not at the existing start strobe.
`nvm_commit` seals and validates the live image at `milan_baremetal.c:833-835`
and only then strobes start at `:845`. A flag cleared at the existing start
would leave the seal and the validation outside the capture, and the seal is
what fixes the CRC-32 the whole commit is checked against. Moving the start
strobe earlier instead is not available either: the deferral branch at
`:836-844` returns without acknowledging, so an earlier start would leave the
commit bracket open on every deferral.

The proposed sequence, with the tracked steps unchanged:

```
arm                                   <- new, before anything reads the image
read back the status word             <- orders the strobe ahead of the loads
refuse if the tag is absent           <- feature probe, section 4.4
release and defer if not armed/valid  <- a producer operation is in flight
seal, validate                        (unchanged, milan_baremetal.c:833-835)
release and defer if cap_valid fell   <- cheap: do not spend an erase cycle
start                                 (unchanged, :845)
erase if the target is not blank      <- unchanged except for the blank skip
program, read back, verify            (unchanged, :846-852)
publish sequence and verdict          (unchanged, :866-867)
ack                                   (unchanged, :868)
read the status word: if ack_ref, say so and leave dirty set
```

Two notes on the read-backs, because the brief is right to be suspicious of
them. The read-back after the arm is an **ordering** device only: it puts the
strobe ahead of the loads this function makes. It is not the atomicity
mechanism. The atomicity is the one-cycle next-state function of section 4.1,
evaluated in the backend's own clock domain, where `milan_csr` and
`KL_pp_shadow` both sit (`milan_datapath.sv` instantiates both on `axis_clk`),
so no crossing separates a strobe from the device face. The read-back after
the acknowledgement is a **report**, not a check: the decision was already
made by the backend.

The contract is monotone in window width. Any transport latency on the
acknowledgement only widens the window and can therefore only refuse more,
never accept a stale image. Latency on the arm is the one direction that would
be unsafe, which is what the read-back after the arm removes.

A verified slot is promoted even when the acknowledgement is refused. It is a
complete image whose digest closes; refusing to promote it would discard a
good newer generation to punish a race, and the next service call commits the
newer state anyway.

### 4.4 What an accepted acknowledgement then means

**The invariant.** An accepted acknowledgement implies that no mutation
occurred between the arm and the acknowledgement, and that the arm was taken
over a completed-record state. Since the backend writes only the record area
and the firmware owns the header and the trailer, the record area is therefore
byte-stable across the whole interval in which the firmware seals it, digests
it, programs it and compares it. The acknowledged slot holds **exactly the
record area as it stood at the arm edge**, and every change that had already
reached the image at that edge is in the slot.

That is the identity the acknowledgement was missing, and it is established by
the window rather than by any property of the bytes. It does not need the CRC
to be a capture mechanism, and it does not need a second status read.

**The one exception, stated rather than assumed.** `dirty` can also be set by
`change_i`, which reports that a persisted field moved, not that its record
has been written. A change that has been captured by the donor's manager but
not yet flushed is therefore not in the image and can be retired by an
acknowledgement that covers the image faithfully. Nothing is lost: the later
WRITE completion marks the image dirty again. Section 9.4 gives the bound and
the owner.

### 4.5 The interface additions

All of them land in space that is free today.

| Where | Bits | Meaning |
|---|---|---|
| backend control word 4 (`PP_NVM_STAT` write, `milan_csr.sv:1995-1999` forwards the whole word) | `[3]` arm, `[4]` release | strobes; `[2:0]` unchanged |
| backend status word 3 (`PP_NVM_STAT` read) | `[16]` `cap_armed`, `[17]` `cap_valid`, `[18]` `gap`, `[19]` `ack_refused`, `[31:24]` tag `0xCA` | `[15:0]` unchanged |
| `PP_STAT` at `0x924` | `[11]` `nvm_gap` | the free bit next to the other section 9 bits (`milan_csr.sv:2059-2067` writes `1'b0` there today; `[23:16]` is also free) |
| firmware verdict nibble | `VD_GAP = 14` | a writer verdict like `VD_ERASE`/`VD_PROGRAM`/`VD_VERIFY`, not a container verdict; 15 stays free |

The tag byte is the house feature-probe pattern (`PP_PRESENT_TAG_C`,
`CHMAP_SNAP_TAG_C`). Firmware that reads zero there refuses to persist and
says so once, rather than silently falling back to the acknowledgement rule
this proposal is replacing. The measured cost of the other mismatch direction
is in section 6.3.

**KLJ2, the durability semantics and the default semantics are unchanged.**
No container field, no verdict order, no A/B rule, no erased-record rule and
no deadline value moves.

## 5. Alternatives, and why they are not selected

| Alternative | Verdict | Technical reason |
|---|---|---|
| **A generation counter**, published by the backend and quoted back at the acknowledgement | **Rejected as the primary mechanism, accepted as equivalent under a width obligation** | It is exactly as strong as the sticky window if and only if the counter cannot return to its captured value inside a window. At the shipping 50 MHz a complete record update measures 257 backend edges in this harness, about 5.1 microseconds, so a producer writing back to back reaches roughly 1.55 million updates inside the 8,000 ms commit deadline: 16 bits wrap 24 times over, 32 bits cannot wrap at all. A sticky bit has no width and no wrap argument to get wrong, costs one flip-flop instead of two 32-bit paths, and needs no comparator. The brief asks about counter wrap; the answer is that no counter is used, and this is why. |
| **A bounded immutable snapshot** copied out of the live image, with producer requests deferred for the copy | **Rejected for this repair, retained as the answer if invalidation-retry ever fails to converge** | It is feasible and its prerequisites are real: the reserved `ppmem` window has room (53,320 of 1,048,576 bytes used at 8x8, so a second 9,224-byte buffer is 0.9 percent more), and the existing device face already supports deferral because the port holds `dev_req_o` until granted, so no new signal is needed. Its bounded pause is a copy, not a flash operation: 1,153 eight-byte lanes at 8x8, about 9,200 backend edges or 184 microseconds at 50 MHz against the harness's three-edge memory bridge. But that arithmetic rests on an **unmeasured** bridge latency (the real arbiter is slower and variable), it still needs the same gap interlock to decide when a copy may start, and the port has **no grant timeout** (`KL_pp_nvm_port.sv:184-211` waits for `dev_gnt_i` forever), so a wedged copier wedges the producer lane with no recovery. The selected design has a zero-length pause and needs none of that. |
| **Clear a sticky changed flag at the existing start strobe** | Rejected | The seal and the validation read the live image before start (`:833-835`). A flag armed at start covers neither, and the seal is what fixes the digest the whole commit is graded against. Moving start earlier breaks the deferral path's bracket. |
| **A second device-busy read, or two status reads, before acknowledging** | Rejected | Neither is atomic with respect to the producer, and both are blind in the ERASE-to-WRITE gap, where `dev_busy` is genuinely low. This is the case the `gap` bit exists for. |
| **A CRC over the image, or comparing the image twice** | Rejected | The seal already computes a CRC-32 over the live bytes, and the read-back already compares them. Together they catch every *smear*, which is why the baseline's `post-seal` and `mid-program` cases end in `VD_VERIFY` rather than in a bad image. What they cannot catch is the *blank*, because a blanked span is a legal encoding whose digest closes. |
| **Export the donor's `nvm_busy_w` and gate on it** | Rejected as a dependency, retained as an optional strengthening | Section 3. It is weaker than what the parent already derives for image consistency, and the accounting problem it would help with (section 9.4) needs manager-level quiescence, not port busy. |
| **Freeze the producer for the flash transaction** | Rejected | The transaction is up to 3.2 seconds of media time (design page section 9.4). Freezing the persistence lane for that long is exactly what the issue forbids, and it is unnecessary: the selected design never defers a producer request at all. |
| **Hold `dirty` asserted whenever anything is uncertain** | Rejected | It would pass every safety test and persist nothing. The `no-change`, `before-window` and `gap-then-close` cases exist to refuse it, and the prototype clears `dirty` in twelve of fourteen cases: the two that end dirty are exactly the two where the producer's logical operation never completed. |

## 6. What the prototype shows

Two benches, one set of sources, under `proposal-evidence/`. Exact commands,
exits and digests are in `proposal-evidence/COMMAND_RESULTS.md`.

The prototype backend and firmware are derived from the tracked files by
**counted, exact textual replacement** (`proposal-evidence/mkproto.py`), so
every difference is auditable and re-derivable. The tracked files are hashed
before and after every run and are unchanged.

### 6.1 The unit bench: the contract as statements

`proposal-evidence/unit/unit_main.cpp` drives `KL_nvm_backend` alone through
its real device, memory and control faces. It grades nineteen contract
statements. The **same** statements grade the tracked module, so the baseline
column is measured rather than asserted, and six single-expression mutants of
the prototype are graded by them too.

| Build | pass | fail | which statements fail |
|---|---|---|---|
| tracked module | 3 | 16 | every acknowledgement statement except the same-edge one, plus every gap statement |
| **prototype** | **19** | **0** | none |
| M1 window never voids | 13 | 6 | `U2.ack_gap_1..64`, `U8.change_pin` |
| M2 acknowledgement unqualified | 3 | 16 | the tracked module's failure set exactly |
| M3 arm ignores the gap | 16 | 3 | `U5`, `U7`, `U10` |
| M4 a completed erase is not a mutation | 17 | 2 | `U5`, `U10` |
| M5 the window outlives its acknowledgement | 18 | 1 | `U11` |
| M6 a same-edge change is reported as retired | 18 | 1 | `U13` |

Every mutant reddens, and each reddens a different set, so the statements are
not one check wearing six hats. M5 and M6 are the interesting pair: neither
loses data, because the `dirty` priority still protects the change. What they
lose is the **report**, so the firmware would believe a commit covered a
change it did not. That is why "an acknowledgement that retires nothing says
so" is a graded statement and not a convenience.

The three statements the tracked module passes are worth naming: the reset
state, the same-edge case (`U2.ack_gap_0`, the protection #418 already
measured) and `U3.clean_window_retires`, which is the non-vacuity check.

### 6.2 The co-simulation: production interfaces

The #418 arrangement, extended. The real backend RTL is compiled from the
checkout; the complete production firmware translation unit is host-compiled
with the repository's own two fence adapters and nothing else; the
repository's own host model supplies flash, time and the boot walk. The
firmware reads the **backend's own status word** for `PP_NVM_STAT`, so every
decision it makes about `dirty`, the window and the gap is made on RTL
evidence. A temporary external scheduler runs producer logical operations
(`ERASE_REGION` then `WRITE`, the envelope the port emits) at named points.

Fourteen cases at the shipping `endstation_ax7101_1x1_tdm8` shape. The oracle
decodes both journal slots with the repository's own `klj2_decode` and reads
the record bytes out of the image; no verdict is taken from a status bit.

| Case | What it schedules | tracked | prototype |
|---|---|---|---|
| `no-change` | nothing | pass | pass |
| `before-window` | an update completes before the commit begins | pass | pass |
| `in-window-preseal` | after the arm, before the seal | not expressible | pass, one deferral then converges |
| `post-seal` | after the seal, on the existing start strobe | **fail**: no image, `dirty` stuck | pass |
| `mid-erase` | during a 3 s flash erase | **fail**: old record, `dirty` stuck | pass |
| `mid-program` | between two page programs | **fail**: old record, `dirty` stuck | pass |
| `post-verify` | the #418 ordering | **fail**: acknowledged, new record lost | pass, refused then converges |
| `on-ack` | the same backend edge | pass | pass |
| `post-ack` | after the acknowledgement | pass | pass |
| `duplicate-ack` | an update, then a repeated acknowledgement | **fail**: the repeat retires it | pass |
| `repeated-updates` | three updates inside one commit, then quiet | not expressible | pass |
| `gap-before-window` | a blanked span, never closed | **fail**: blank promoted, `dirty` cleared | pass, held, saved image stands |
| `gap-then-close` | the same span, closed later | **fail** at the first checkpoint: blank promoted | pass |
| `failed-write` | ERASE fine, WRITE fails, another record dirties the image | **fail**: blank promoted permanently | pass |

Tracked: 8 of 12 runnable cases violate the contract. Prototype: 0 of 14, in
both the plain and the pre-erase firmware variants. `mutant-M1` in the same
co-simulation violates `post-verify`, so the integration test can also fail
for the defect it claims to detect.

Convergence is graded, not assumed: every case that ends `dirty = 0` also has
the newest accepted slot holding the newest completed record, and the three
gap cases that end `dirty = 1` are exactly the ones where the producer's
logical operation never completed. No case passes by leaving `dirty` set.

Two transcript lines carry the repair:

```text
Milan NVM: commit (dirty) seq 1 -> slot A, 2696 B, verified; NOT acknowledged, the image moved.
Milan NVM: commit (dirty) seq 2 -> slot B, 2696 B, acknowledged.
```

```text
Milan NVM: a record span has been blank for 500 ms; persistence is held and the last verified slot stands.
```

### 6.3 The mismatched build

Prototype gateware with tracked firmware was run as a control. The firmware
never arms, so every acknowledgement is refused, `dirty` never clears and the
service loop commits on every debounce: five acknowledgements and five erase
cycles per case instead of one. That is the argument for shipping both halves
together and for the feature tag, which protects the other direction (new
firmware, old gateware) by refusing to persist rather than by losing data.

## 7. Quantities

### 7.1 The capture window, measured and derived

The window is the interval a producer update can void. Nothing is frozen
during it; the only cost of a collision is that the commit is retried.

Measured in the host model, `mid-erase` case with a 3 s modeled flash erase:

| firmware variant | window | erase cycles spent |
|---|---|---|
| plain | 3,012,909 us | 2 |
| with pre-erase | 12,803 us | 1 |

Derived from the media, using the design page's own section 9.4 inputs
(N25Q128 maxima `tSE` 3 s and `tPP` 5 ms, LiteSPI at 12.5 MHz, 8 clocks per
byte), which is the honest bound rather than the model's:

| shape | image | window, plain | window, pre-erased | ratio |
|---|---|---|---|---|
| `endstation_ax7101_1x1_tdm8` | 2,696 B, 11 pages | 3,060 ms | 60.2 ms | 50.8x |
| `endstation_ax7101_8x8` | 9,224 B, 37 pages | 3,203 ms | 202.7 ms | 15.8x |

Pre-erase is a **firmware-only, optional** item: erase the slot that is not
authoritative while the debounce runs, instead of inside the window. It costs
no extra erase cycle (the same slot is erased once per commit either way), it
never touches the authoritative slot, and the A/B property holds at every
instant. It is presented separately because the contract does not need it; it
is what makes convergence comfortable under a controller that issues a dozen
SET commands in a row.

Unmeasured inputs, named rather than absorbed: the real `tSE` on the fitted
parts is far below the datasheet maximum; the CPU-side loop overhead, the
memory-mapped QSPI read rate under the real controller and the DDR arbiter's
latency are not measured anywhere in this proposal.

### 7.2 Producer pause

## 8. Three clocks, and what each one proves

They are not commensurable and the proposal does not add them.

- **Backend clock edges.** The RTL advances only during modelled
  transactions. Edge counts and orderings are real: grants, completions, the
  same-edge coincidence and the window's next-state function. At the shipping
  50 MHz an edge is 20 ns, but elapsed backend time in this harness is not
  elapsed host time.
- **Host model milliseconds.** The firmware's own busy waits advance a
  counter. Debounce, heartbeat cadence, flash durations and the window widths
  of section 7.1 are in these units. They are the model's, not a board's.
- **Board and SoC time.** Not modelled at all. No RV32I core, no LiteX CSR
  bridge, no memory arbiter, no SPI device, no donor port or manager is
  instantiated.

One consequence must be stated plainly because it bounds several results: the
backend's millisecond divider is 50,000 edges at the shipping clock and the
whole harness runs a few thousand edges, so `ms_tick_w` never asserts. The
deadline machine, `loss_w`, `nvm_stale` and the 8,000 ms bracket lapse are
therefore **unexercised**. This is the same limit R28 quantified on #418. It
is also why the release strobe matters for the evidence as well as for the
product: without it a failed commit could not retry inside the observation
window, and the baseline's `post-seal` and `mid-erase` non-convergence is
partly that artefact rather than purely a contract result.

## 9. What remains unproven

### 9.1 No producer implementation evidence

The donor port and manager are not instantiated. The producer is a
bus-functional model whose envelope matches `KL_pp_nvm_port.sv:354-372` and
whose record delta is a field the donor really projects and serialises. That
establishes **interface compatibility and backend consequence under a
permitted schedule**. It does not establish the waveform a real AECP command
produces through the donor pipeline, nor how often the vulnerable window is
hit on a board. **This dependency remains unverified.** #420's producer to
backend audit is the lane that owns closing it, and this proposal should not
be read as a complete repair until it does.

### 9.2 The gap tracker's single entry

`gap_open`, `gap_region` is exact while the initiator keeps one operation
outstanding, which the port's F02.8 manager face requires. That is a property
of the pinned donor, checked by reading it, not by simulating it. A second
concurrent producer would make `gap_stuck` reachable, and the design's answer
there is to refuse rather than to guess. If #70's P4 manager brings a second
initiator, this is the line that has to be revisited.

### 9.3 The 8x8 shape

The co-simulation runs the 1x1 shape only. The 8x8 shape is covered by the
area measurement, the elaboration bounds and the record-space gate, not by the
case matrix.

### 9.4 The change pin can still retire an undebounced change

`nvm_change_w` in `KL_pp_shadow.sv:892` is the rising edge of a sticky level,
so it fires once per power cycle, at the first persisted-field write, before
the donor's debounce has flushed anything. An acknowledgement can therefore
retire that first `dirty` while the record is still only in the donor's shadow
store. Nothing is lost, because the later WRITE completion marks the image
dirty again and the next commit converges, and the exposure is bounded by the
donor's `DEB_TICKS_P`. But `(backed, dirty, stale) = (1, 0, 0)` is briefly
optimistic once per power cycle. Closing it needs manager-level quiescence
from the donor, which is the optional strengthening of section 3 and belongs
to #420's accounting rather than here. **Named, not repaired.**

### 9.5 Adjacent observations, deliberately not fixed here

- A reported `VD_ERASE`, `VD_PROGRAM` or `VD_VERIFY` does not revoke
  `nvm_backed` in the RTL; only the deadline does. The design page's section
  9.2 says a reported failure should. The release strobe makes the retry
  prompt but does not implement that revocation.
- `tb/verilator/nvm_backend/sim_main.cpp:810-812` asserts `(1, 0, 0)` after a
  change followed by an acknowledgement, which is the outcome this contract
  changes. The shipped suite has to be re-graded by the implementation, not
  left to pass unchanged.

## 10. The one decision an owner has to make

Everything else in this document is an engineering choice inside an existing
requirement. This one changes an owner-visible behaviour.

**When a record span has been blanked and the producer does not close it, what
should the device do?**

- **(a) Hold persistence and keep the last verified slot. Proposed.** The
  saved image stands, `nvm_dirty` stays 1, `nvm_gap` is published and the
  firmware says so once after 500 ms. Nothing is lost that was ever saved. The
  cost is that persistence of *all* records stops until the span closes or the
  device resets, because the image is written whole.
- **(b) Commit the blank after a timeout.** Persistence keeps working, and the
  record that was mid-update reverts to its vendor default on the next power
  cycle. That is a new loss policy: it makes a producer failure destroy a
  controller-set value rather than merely fail to update it.

(a) is proposed because #70 exists to remove false success, and because Milan
5.3.8.2 and 5.3.8.3 make the bound state reportable rather than optional. It
is stated here because it is a policy, not a derivation.

The 500 ms bound is derived, not chosen: the normal ERASE to WRITE transition
is a handful of core clocks, the donor's bounded retry adds at most
`RETRY_MAX_P` re-serialisations of a 28-byte record, and the donor's own
commit debounce is `DEB_TICKS_P = 500` at a 1 ms tick. A gap outliving one
donor debounce window cannot be a normal transition. The value lives in
firmware, where a bench can change it without touching gateware.

## 7. Adapter changes, stated explicitly

The co-simulation reuses #418's arrangement. What differs, and why:

1. **The bridge** (`harness/proto_bridge.cpp`) adds three entry points to the
   frozen one: the halves of a producer logical operation separately
   (`rtl_record_erase`, `rtl_record_program`), a WRITE whose first memory
   transaction the bridge fails, and a reset pulse. It also logs the four new
   status bits. It drives only public module ports.
2. **The host model adapter** now takes `PP_NVM_STAT` **entirely** from the
   backend's own status word rather than overwriting selected fields of the
   model's copy, so every firmware decision about `dirty`, the window and the
   gap is made on RTL evidence. It adds a trigger and action scheduler, and
   replaces the model's `--change` parser with real device commands. The
   adapter is compiled with `-Wno-unused-function` because that replacement
   leaves the model's hex helper unreferenced; the firmware translation units
   keep the full `-Wall -Wextra -Werror` set.
3. **The firmware** is the tracked translation unit for the baseline and the
   mismatch builds, with the repository's own two fence substitutions and
   nothing else. For the prototype builds it is
   `prototype/milan_baremetal.proto.c`, derived by counted replacement, plus
   the same two fence substitutions. The fence count is asserted to be exactly
   two in every build.
4. **The RTL** is compiled directly from the checkout for the baseline, and
   from `prototype/` or `mutations/` otherwise. No tracked RTL is modified.
5. Every model directory is deleted before its build, because Verilator's
   generated makefile does not treat the objects passed through `-LDFLAGS` as
   dependencies and would otherwise link a stale binary. This was a real
   defect in an earlier run of this harness and is recorded here rather than
   quietly fixed.
