# Gateware `0x0014` on silicon — the area round placed, met timing, and flashed

*2026-07-27. The first bitstream carrying the five-queue map and the area
recovery, built, flashed and probed on the AX7101.*

The question this round had to answer was narrow: **the six-queue build missed
placement by 282 slices — does the recovery fit, and does it still meet
timing?** The second half mattered more than it looks, because the previous
8×8 failure was a *timing* miss, and every area figure carried into this build
was a yosys estimate under a calibration band. Exactly one number in the whole
ladder had ever been a Vivado result.

Both halves are now answered on hardware.

## What the estimates got right, and by how much

The lane predicted **−4,847 LUT** (hierarchical yosys) for its four logic
levers, plus a Vivado-proven −428 for the LPF prune and an estimated −812…−1,224
for the queue reduction. Delivered: **−5,216 LUT** measured Vivado-to-Vivado.
The estimate was good.

**Slice occupancy barely moved** — 99.93 % → 99.65 %, fifty-five slices free —
even though 5,216 LUTs came out. That is the packing non-linearity the lane
warned about, stated as a caveat and now visible as a measurement: LUT count and
slice count are not proportional at this occupancy, and the design is still
slice-bound. **The recovery was necessary and barely sufficient.** The six
banked tier-1 prune levers ([`AREA_BUDGET.md`](../design/AREA_BUDGET.md)) were
deliberately not spent and remain the headroom.

## Flashing: bitstream only, and why

Only the gateware changed, so only the gateware was written. The full-image
path (`deploy.sh flash-images`) ceilings rootfs at 16 MiB and would have erased
the `journal` and `user` regions for no benefit.

The layout makes the bitstream-only write provably safe:

| region | offset | budget | actual |
|---|---|---|---|
| bitstream | 0 | 4,194,304 | **3,825,992** (368 KB spare) |
| kernel | 4,194,304 | 3,145,728 | untouched |
| opensbi / dtb / rootfs | 7,340,032 + | — | untouched |
| `journal` / `user` (reserved) | 14,548,992 / 14,680,064 | — | untouched |

**Pre-flash CSR check.** `csr.csv` differed from the previous build by six
lines, all cosmetic — a timestamp and the CPU-ISA string with identical
extensions in a different order. **No address moved**, so the DMA window map the
deployed kernel and DTB expect was unchanged. That check is not optional here:
a shifted window map under an unchanged DTB is the 2026-07-24 CSR-rot class.

> **Incidental finding — `csr.csv` is not byte-reproducible across builds.**
> The three seeds differ in `config_cpu_isa`, which lists the same extensions in
> a different order each time. Cosmetic, but it would defeat any byte-comparison
> gate over that file; compare addresses, not bytes.

**Cable identified by type, not by guesswork.** The FTDI serials are
deliberately not committed, and both boards are `xc7a100t`, so an IDCODE check
cannot tell them apart — picking wrong writes an AX bitstream into the Arty's
boot flash. The discriminator is the cable *type* `board_facts` already records:
`-c ft232` enumerates and reads `idcode 0x3631093` on one adapter and fails on
the other, which is the Arty's `digilent` FT2232.

## On-silicon verification

| check | value | verdict |
|---|---|---|
| `ID` `0x000` | `0x4D494C4E` = "MILN" | ok |
| **`VERSION` `0x004`** | **`0x0001_0014`** | the new gateware is running. **This record stays at `0x0014`: that is what is flashed.** The tree moved to `0x0001_0015` on 2026-07-27 (the ADP shape registers became read-only) and then to `0x0001_0016` (the AVTP `tu` bit is driven, `0x778` clock-validity group), and no bitstream has been built from either — a board reading `0x0014` still has RW `0x618`/`0x61C`, still needs the boot-script counts to advertise anything at all, and still stamps `tu = 0` on every frame whatever its clock is doing |
| `CAP` `0x008` | `0x00407F05` — low byte `0x05` | **five queues, in hardware** |
| `CLS_CTRL` `0x300` | `0x0000_0005` | `use_pcp` + `ctrl_class`, per spec |
| `CLS_TCQ` `0x310` | `0x0048_98C0` | the five-queue TC map, per spec |
| CBS `0x400`–`0x480` | 25 / 50 / 50 / 150 / 450 Mb/s | **725 Mb/s = 72.5 %**, under the 75 % ceiling |
| CBS `0x4A0` | `0x0000_0000` | the five-queue carve-out is real |
| `hostplane_smoke.sh` | **5/5 PASS** | RX +83,842 / 15 s, ts-ring advancing, `AAF_CTRL=0x00020003`, ALSA module loaded |

**The datapath is live.** The RX stream-parser probes tick at roughly
**15,900 frames/s**, and read back-to-back in one shell invocation,
`parsed == matched` **exactly** (`0x009A0583`) — every parsed stream frame is
matched by the stream table. With `SNAP` armed, the per-stream counters return
real values rather than zeros.

## Two traps this round re-confirmed

Both are already written down. Both caught me anyway, which is why they are
worth repeating.

1. **The `0x800` window reads zero until `SNAP` is armed.** `STRMW_CNT[0..9]`
   all read `0x00000000` on a direct read and look like a dead counter block.
   Write `SEL`, write `SNAP[0]`, poll busy, *then* read — and the same registers
   return 5.1 M / 4.8 M / 9.9 M. A zero from that window is not a measurement
   unless the snapshot was armed.
2. **`devmem` costs roughly 0.75 s per call, which is enough to fake a defect.**
   Reading `parsed` and `matched` in separate calls made `matched` look *larger
   than* `parsed` — impossible, and alarming, and purely an artefact of the two
   free-running counters being sampled seconds apart. Read counters that must be
   compared in one invocation, or through `SNAP`.


## The bench is wrong, and it is a one-line config: priority1 238

Found 2026-07-27 while checking stream health on the flashed board, after a
first pass wrongly reported the datapath healthy (see the trap below).

**Every entity on the segment has elected the AX7101 as grandmaster — including
a Milan-validated reference device.** Decoded from the ADPDUs on the wire:

| device | entity_id | advertised gPTP grandmaster | T/L |
|---|---|---|---|
| reference device `3c:c0:c6:01:02:03` | `3CC0C60102030000` | `020000FFFE000001` | 4/10 |
| peer host | `6805CAFFFE95B2D1` | `020000FFFE000001` | 8/8 |
| Arty | `020000FFFE000002` | `020000FFFE000001` | 1/2 |
| **AX7101** | `020000FFFE000001` | **itself** | 1/2 |
| `00:e0:4c:88:11:90` | `00E04C8811900016` | `0000000000000000` (unsynced) | 0/0 |

**Cause.** `/etc/gptp.cfg` on the AX ships `gmCapable 1`, `priority1 238`,
`clockClass 248`. Lower `priority1` wins BMCA, so 238 beats every conformant end
station at 246 — this is not a clock-identity tie-break, it is our board
configured to claim the role. The [historical Milan traceability](../traceability/milan-v12.md)
M-DEV-1 (Milan 4.2.6.2.1) requires **246**, [`../design/TIME_SYNC.md`](../design/TIME_SYNC.md)
says "the shipping priority1 must be 246; the bench 100 override is bench-only",
and the reference switch itself claims 246. **238 is neither** — an undocumented
third value that happens to outrank everything.

**Consequence, measured on the flashed board.** An FPGA on a free-running
oscillator is now the time source for the whole segment, and its own media clock
is unstable: `MEDIA_LOCKED` = `MEDIA_UNLOCKED` = `MEDIA_RESET`, climbing ~8 per
minute. Listeners comparing presentation times to that wandering base see

    LATE_TIMESTAMP  5,122,912
    EARLY_TIMESTAMP 4,766,414
    FRAMES_RX       9,893,436     -> late + early ~= every frame, none on time

The compliance record predicted exactly this: *"a wrong priority1 changes who
wins BMCA in every customer install, not just the bench."*

**Not fixed here.** The change is one line, but the first pass on this board
reported health from a subset of counters, so the discipline is to change it and
then **re-measure all ten counters on both boards** before claiming anything.

> **The trap, recorded because it caught me.** `AVTPRX_ERR` (`0x6C0`) was frozen
> and `parsed == matched` exactly — and both were true and both were irrelevant.
> That register covers only SEQ_NUM_MISMATCH, UNSUPPORTED_FORMAT and
> TIMESTAMP_UNCERTAIN, which really were near zero. MEDIA_UNLOCKED and
> LATE/EARLY_TIMESTAMP live in the `0x800` window, which I read **and did not
> decode**. A frozen error register beside nine million bad timestamps is the
> reads-that-lie pattern in
> [`RECURRING_DEFECT_PATTERNS.md`](../limitations/RECURRING_DEFECT_PATTERNS.md).
> Read all ten `A_STRMW_CNT` words with their names attached, on both boards,
> twice.

## Honest limits

* **This is one board, one shape, one bitstream.** The Arty was not rebuilt or
  reflashed; it still runs its previous gateware.
* **The analog audio record does not carry over.** The −147.99 dBFS loop
  measurement was taken *through* `KL_pcm_lpf`, which this build prunes
  (`LPF_P = 0` on ax7101). It must be re-measured against this bitstream before
  it is quoted, and it is not re-measured here.
* **No audio, latency or link-bounce testing is in this page.** Identity, the queue map, the smoke test and datapath liveness are
  established; the torture campaign is not.
* Fifty-five free slices is not comfortable margin. Any future addition to the
  datapath should expect to spend a banked lever.
