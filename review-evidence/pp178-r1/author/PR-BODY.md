[A634]

SET_CONFIGURATION: no notification without a change; NO_SUCH_DESCRIPTOR for a missing configuration.

Closes #178
Refs #179 (see "Testbench item A3" below: one acceptance item names a testbench item that tests READ_DESCRIPTOR, not SET_CONFIGURATION)

## What changes

Both fixes are in the SET_CONFIGURATION micro-program `E_SCFG` (`hdl/aecp/ucode/gen_ucode.py`). No RTL file changes, so there is no register-map, port or parameter change. No existing entry point moves, and the engine's µPC map is untouched.

**#178: an unchanged index sends no unsolicited notification** (Milan v1.2 5.4.5.2: only a command that "modifies the state"; it narrows IEEE 1722.1-2021 7.4.7's "on success this command also sends an unsolicited notification").
`E_SCFG` already compared the new index with the one in force and skipped `NOTIFY_ENQ` on equality, but with the operands in the wrong slots. The µCPU's `COMPARE` narrows only `ra` to the format and takes `rb` whole. The index in force was in `rb` (r6). Before the first SET, r6 is the image ENTITY's lane at byte 304, which holds `configurations_count` above `current_configuration`, so the two never compared equal. That is the silicon observation (SUCCESS, then u=1 to the registered controller). The fix is `COMPARE ra=6, rb=12`: r6 is narrowed to the index, and r12 holds the index alone. A real change still notifies once, to every registered controller except the requester.

**#179: a configuration_index with no CONFIGURATION descriptor answers NO_SUCH_DESCRIPTOR** (IEEE 1722.1-2021 Table 7-141; 7.4.7.2 sets no status for it; owner decision 2026-10-17).
The range check (`index < configurations_count`) now branches to a new arm, `E_SCFGNSD` (ROM words 1553..1565, previously free). The arm answers NO_SUCH_DESCRIPTOR carrying the current index (7.4.7.1, "the old value if it fails"), through the same current-value overlay and response body as the other refusals. A command too short to carry the index stays BAD_ARGUMENTS.

| Order | Case | Answer (cdl 16, current index) |
|---|---|---|
| 1 | cdl < 16 | BAD_ARGUMENTS (unchanged) |
| 2 | any Stream Input bound or Stream Output streaming | STREAM_IS_RUNNING, ahead of the lock and the index (Milan 5.4.2.5; unchanged) |
| 3 | locked by another controller | ENTITY_LOCKED (unchanged) |
| 4 | index >= configurations_count | **NO_SUCH_DESCRIPTOR** (was BAD_ARGUMENTS) |
| 5 | otherwise | SUCCESS; one notification only if the index changed |

## Testbench item A3

Issue #179 says "testbench item A3 asserts BAD_ARGUMENTS" for SET_CONFIGURATION. In `tb/pp_top`, item A3 is READ_DESCRIPTOR with configuration_index 3. It is a READ_DESCRIPTOR check, and the assignment keeps READ_DESCRIPTOR unchanged. So A3 is left as it is. The suite's SET_CONFIGURATION out-of-range items are W18d and W18d2. Those are updated, and the new SC1-SC3 carry the planted mutants. Please confirm that this meets #179's A3 item before closing #179.

## READ_DESCRIPTOR for a missing CONFIGURATION index (reported, not changed)

- A CONFIGURATION descriptor_index the image lacks (configuration_index 0) is a locate miss: NO_SUCH_DESCRIPTOR with the 4-byte stub, cdl 20. That is the same status SET_CONFIGURATION now gives.
- A configuration_index field at or past configurations_count is BAD_ARGUMENTS for every descriptor type, ENTITY and CONFIGURATION included (item A3). IEEE 1722.1-2021 7.4.5.1 says that field "is ignored on receipt" for ENTITY and CONFIGURATION reads. That is a separate question, left open here.
