## Description

**Cause.** act mounts one volume, the tool cache at `/opt/hostedtoolcache`, into every job container of a replay. Each job's `HOME`, `RUNNER_TEMP` (`/tmp`) and workspace are its own. `actions/setup-python` resolves the elaboration interpreter from that cache, and the LiteX install, the VexiiRiscv clone and submodule update, the cached CPU metadata copy, the patch series and the Scala generation all write into that interpreter's site-packages. Two `elaborate` legs started together therefore clone into one directory and contend for one git lock, and reverse each other's patches: the two failed #745 replays.

**Fix (the assignment's first option).** The `elaborate` template gains one setup step after setup-python:

```sh
set -euo pipefail
python3 -m venv "$RUNNER_TEMP/litex-venv"
echo "$RUNNER_TEMP/litex-venv/bin" >> "$GITHUB_PATH"
```

Every later step's `python3` is then the job's own venv, so it installs, fetches and patches only there; the tool cache is only read. No other step's text changes.

## Known limitations / out of scope

- The four-job act replay at this head is the coordinating role's receipt; this PR shows the isolation natively.
- Under act each leg now does its own VexiiRiscv placement and Scala generation instead of finding the other leg's in the shared tree, as hosted runners always have. Its effect on the replay's wall clock is read from that replay.
- The control plants a copy of a local CPython 3.12 rather than the runner image's 3.12.14. It runs every step of the shared window except the cache restores and `Install sbt`, which it names with the reason; a new step in that window that it neither runs nor names makes it refuse. With `--gate-legs` it also runs the gate steps, and names what it leaves out after the patch series: the RV32 SDK restore and install (an installed SDK is linked into each leg's home, so natively both legs read one SDK directory), the Verilator steps and the LiteX aggregate (which need the pinned Verilator build), and the hosted receipt and upload steps.
- The patch-check refusal is judged from the builder driver's receipt format; a check absent from the receipt is reported as "did not run", and a receipt it cannot read stops the control with an error and a non-zero exit, never a pass.
- The act runner and its shared tool-cache volume are unchanged, as the assignment decided.
