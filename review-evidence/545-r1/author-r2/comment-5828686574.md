### F3 MINOR: the connected "covers the PHC tail" check copies the RTL's assumption instead of measuring the PHC

- **Lenses:** Tests.
- **Where:** `tb/verilator/milan_dp/sim_gmstep.cpp:282` and `:420-442` (the expected level is `raw || any(4-sample history)`); `:1082`. The claim is made in `tb/verilator/milan_dp/README.md:895` and `docs/design/TIME_SYNC.md:232`.
- **Evidence:**
  - The harness's expected value is built with the same formula as `hdl/milan/milan_datapath.sv:2762-2767` (four delay samples). It does not look at the PHC's applied rate at all.
  - Suppose the addend's application latency grows, for example by one more register between `gptp_adj_w` and `timestamp_counter.adj_i`. The RTL tail and the harness model would still agree, and the check would stay green with one slewed sample uncovered per release.
  - My probe measures against ground truth instead. It uses the real `ptp_csr_sync` and `timestamp_counter`, the shadow's one-register latch, and the alignment block extracted verbatim from the datapath. The shipped 4-stage tail covers every slewed sample: 96 slewed, 0 violations. A 3-stage control misses exactly one sample per release: 3 violations (`receipts/tail_probe.txt`, `scripts/tail_probe/`).
  - So the RTL is right today, but the connected check could not show it.
- **Authority:** AGENTS.md section 6, Tests ("Tests do not merely reproduce implementation assumptions").
- **Impact:** The documented guarantee ("every release-tail edge") is not protected against a change in PHC pipeline depth elsewhere in the datapath.
- **Required outcome:** Grade tail coverage against the PHC itself, either the applied addend at the counter (`phc_adj_ts_w`) or the counter's per-cycle increment. A control that adds one addend-path stage while keeping the 4-cycle tail must fail.
- **Verification:** that control fails the connected check, and the head passes.
