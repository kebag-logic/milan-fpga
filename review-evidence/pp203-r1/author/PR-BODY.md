[A699] AECP REBOOT (IEEE 1722.1-2021 §7.4.43): answer SUCCESS, notify, send ENTITY_DEPARTING, then hold reboot_req_o

Closes #203

## What it does

A controller's REBOOT of ENTITY 0 (IEEE 1722.1-2021 §7.4.43, Figure 7-68) is answered SUCCESS with the
command's four bytes echoed at cdl 16. The processor then tells the other registered controllers,
sends ENTITY_DEPARTING where the entity was advertising, and raises the one new top-level output,
`reboot_req_o`. That output is a level, held until `rst_n`. The reset itself, and what the end
station restores after it, are the integrator's (milan-fpga #787).

| Command | Answer (every answer is `{descriptor_type, descriptor_index}` at cdl 16) |
|---|---|
| cdl < 16, too short for Figure 7-68's four bytes | `BAD_ARGUMENTS` |
| any descriptor_type but ENTITY (this build has no MEMORY_OBJECT firmware image, §7.4.43.1's other target) | `NOT_SUPPORTED` |
| ENTITY at any index but 0 | `NO_SUCH_DESCRIPTOR` |
| ENTITY 0 under another controller's lock (§7.4.43.2, §7.4.2) | `ENTITY_LOCKED` |
| ENTITY 0, otherwise (a padded command included) | `SUCCESS` |

`ENTITY_ACQUIRED` (§7.4.43.2, §7.4.1) cannot arise: this entity is never acquired (Milan v1.2 §5.4.2.1,
ACQUIRE_ENTITY is refused `NOT_SUPPORTED`), and a test shows it. The type and index refusals come before
the lock check, as START/STOP_STREAMING's do. Neither standard orders them.

**The notification.** §7.4.43 says "On success this command also sends an unsolicited notification".
§7.5.2 lists REBOOT, and Milan v1.2 §5.4.5.2 makes the notification a SHALL to every registered
controller but the requester. It rides class 9, the `{type, index}` body of START/STOP_STREAMING's
notification, with REBOOT's opcode in the job's first argument.

**Acceptance and no further command.** The REBOOT is accepted at its SUCCESS response's TX grant. A
refusal, or a response the memory voided into `ENTITY_MISBEHAVING`, leaves the entity in service. From
the grant the AECP engine takes no command from its queue, while its unsolicited path stays open for
the notifications. The top discards, whole, every frame that starts on `rx_*` after it, so no ACMP,
ADP or AECP command reaches an engine.

**The request.** The top reads `tx_*` itself: a frame has left when the MAC takes its last byte
(`tx_valid_o`, `tx_eof_o` and `tx_ready_i` in one clock). It waits for, in order:

1. the SUCCESS response;
2. the REBOOT's notification round: no command notification queued or in its round, and no
   unsolicited frame in flight;
3. ENTITY_DEPARTING. ADP's effective enable falls for good, which is Milan v1.2's SHUTDOWN event. Each
   advertise machine that is advertising sends ENTITY_DEPARTING, and one that is DOWN sends none. The
   top waits until ADP has nothing left to build, queue or send.

Then `reboot_req_o` rises and is held until `rst_n`. It does not wait for persistence. An integrator
that must keep a change accepted just before the REBOOT holds its reset until
`(|nvm_unflushed_o) | d3_unflushed_o` is 0 (documented in 02 F02.10 and the integrator guide). A MAC
that never takes a frame holds the request back, as it holds every frame.

## Where ENTITY_DEPARTING comes from (the clause the issue asked for)

- Milan v1.2: §5.2 is the chapter's overview only. The requirement is §5.6.3: the SHUTDOWN event
  ("Request to shut down the PAAD-AE", §5.6.3.3), WAITING/SHUTDOWN (§5.6.3.5.8) and DELAY/SHUTDOWN
  (§5.6.3.5.11), each "Send an ADP ENTITY_DEPARTING message". Table 5.51 ignores SHUTDOWN in DOWN, so an
  entity that is not advertising sends none.
- IEEE 1722.1-2021: §6.2.1 introduces the Advertising Entity and Advertising Interface state machines.
  The send is `doTerminate` (§6.2.4.1.3, §6.2.5.1.1) and `txEntityDeparting()` (§6.2.5.2.2, Figure 6-3).
  §6.2.6 is the Discovery state machine of the receiving controller, which removes the entity on
  `rcvdDeparting` (Figure 6-4). §6.2.2.15: available_index resets after it.
- The figure: REBOOT's format is IEEE 1722.1-2021 Figure 7-68 (Figure 7-75 is AUTH_ADD_KEY).

## Tests and mutants

New section RBT in `tb/pp_top` (`make -C tb/pp_top reboot`; the default build runs it): 79 checks. It boots
a fresh processor for each SUCCESS and logs every frame the MAC takes with the clock of its last byte.

- RBT1 to RBT4: every refusal on one boot, byte-exact at cdl 16 and each followed by no acceptance, no
  request, no notification to the registered controller, and a command still served. The cases are
  cdl 12 and 14 (`BAD_ARGUMENTS`); MEMORY_OBJECT 0, AUDIO_UNIT 0 and CONFIGURATION 0 (`NOT_SUPPORTED`);
  ENTITY 1 and 0x7FFF (`NO_SUCH_DESCRIPTOR`); and ENTITY 0 under another controller's lock
  (`ENTITY_LOCKED`), where the type and index refusals keep their own answers.
- RBT5: ACQUIRE_ENTITY is `NOT_SUPPORTED`, so `ENTITY_ACQUIRED` cannot arise.
- RBT6: the lock holder's REBOOT with three controllers registered. SUCCESS byte-exact; the notification
  (u = 1, each entry's sequence_id) to the other two and none to the requester; one ENTITY_DEPARTING
  byte-exact. On the wire the order is response < notifications < DEPARTING < `reboot_req_o`, and the
  request is held to the end. A command queued behind the REBOOT is never served, and an AEM command,
  an ACMP GET_RX_STATE and an ADP ENTITY_DISCOVER sent after it go unanswered.
- RBT7: the MAC holds the SUCCESS response's last byte for 30 ms. The engine has accepted, and
  `reboot_req_o` stays 0. Released, the request follows the response.
- RBT8: not advertising, a padded command: SUCCESS at cdl 16, the notification, no DEPARTING, and the
  request after both frames.
- M9 sweeps 0x002A on every non-AEM message type; A5b drops REBOOT; `tb/aecp_cmds` records the three
  programs and the class-9 job's 0x002A, and its sweep resets the engine after each accepted REBOOT.

Seventeen arms in `tb/pp_top/aecp_dispatch_mutants.py` (target `reboot`) are all KILLED by name.
`rbt-request-at-acceptance` is the requested "request raised before the response is sent" (RB_RUN goes
straight to RB_REQ). RBT7 fails it: `RBT7 reboot_req_o stays 0 while the MAC holds the SUCCESS
response's last byte`, 12 failing checks. The others drop each wait (the response, the notification
round, the unsolicited frame in flight, SHUTDOWN, the ADP frame and its flight), make the request a
pulse, remove the frame gate, the engine hold, the SUCCESS-only acceptance, each refusal route, the lock
check, the notification and its command_type. `a5b-reboot-success-arm` (issue #74) is retired, because
SUCCESS is now the answer. Six patch-based arms and one d3 arm whose context moved are re-cut to plant
the same defect.

## Open risks for the integrator

- Adopting this pin with `reboot_req_o` absent from KL_pp_shadow's instance fails the parent's RTL lint
  ratchet (`hdl/milan` 3 > 2, `PINMISSING reboot_req_o`). The adoption has to name the pin: wired to the
  reset (milan-fpga #787) or, until then, open with a rationale.
- Until #787 wires the reset, a controller's REBOOT takes the entity off the network until the next power
  cycle or reset. The parent's findings record a bench tool that once sent 0x002A by mistake: such a
  tool now reboots the entity.
- The request does not wait for persistence. See above.
- Area: milan-fpga's area budget records 16 of 15,850 slices left on the shipping route. yosys shows this
  change neutral, but a Vivado route at adoption is the deciding measurement; none was run here.
- A response the memory voids into `ENTITY_MISBEHAVING` leaves the entity in service, but the REBOOT
  notification queued before it still goes out, as it does for every notifying command whose response
  memory fails.
