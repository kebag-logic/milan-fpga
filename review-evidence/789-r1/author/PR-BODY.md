## Description

**The problem (#789).** `rtl-fast`'s `yosys-elaboration` built pinned Yosys itself, under a cache key that hashed
`.github/workflows/*.yml`.
- Every head that edits a workflow rebuilt it cold inside the job's 30 minutes. At `847eb4dd` the build took
  16 min 33 s (job 121450772865), then the job was cancelled at 30 minutes.
- `ci-fail-fast` then cancelled every run of the head (PR #788 review R705-1-02).

This PR builds Yosys once, in a job of its own, under a key that no workflow edit changes.

| piece | change |
|---|---|
| `scripts/ci_gate_workflows.py` | rtl-fast's derivation `fast_yosys_tool`, modelled on rtl-full's `separate_yosys_build`. It moves `yosys-elaboration`'s template "Cache the pinned Yosys build" and "Build Yosys from source on cache miss" steps into a new `yosys-tool` job ("Prepare pinned Yosys"). That job has the consumer's `needs`, `if` and `runs-on`, and `timeout-minutes: 30`. The templates are unchanged. |
| the tool key | `yosys-${{ env.YOSYS_VERSION }}-86f2ddebce7e98ce7cacc27e8a5c14cb53b51b51-recipe-06e5a02fa8b585ca1b3cc3153245cd97f8b1009666d3b15728f325ed9bd22279-ubuntu-24.04-${{ runner.os }}` is the pinned version and source commit, then the SHA-256 of the template build step (sorted compact JSON, every key), then the runner image label and `runner.os`. It contains no `hashFiles`. |
| `yosys-elaboration` | needs `[changes, yosys-tool]`. Its two build steps are replaced by one `actions/cache@v4` restore of `/opt/yosys` under the same key, with `fail-on-cache-miss: true` and no `restore-keys`. It never builds Yosys. Its timeout stays 30. |
| `rtl-fast` aggregate | gains `yosys-tool` in `needs`, `YOSYS_TOOL_RESULT` and its pair in the verdict loop. A failed build skips `yosys-elaboration`, and the verdict counts a skipped job as a pass, so without this the verdict would stay green. |
| `.github/workflows/rtl-fast.yml` | regenerated by the generator only. Against dev, the jobs that differ are `yosys-tool` (new), `yosys-elaboration` and `rtl-fast` (above), `ci-manifest` (`needs` gains the job) and `ci-fail-fast` (`EXPECTED_JOBS` gains "Prepare pinned Yosys"). Every other job, `publication-census` included, and the other three workflows are byte-identical to dev. |
| `scripts/ci_gate_workflows_selftest.py` | `fast_tool_controls`: see [New checks](#new-checks). |
| `docs/testing/CI_WORKFLOWS.md` | the tool job, its key and evidence; `publication-census`'s key sentence corrected; the one key that differs under "Source-tool cache provenance", and the re-run-all rule after a failed cache save. |

### New checks

`fast_tool_controls()` runs in the hosted "CI scheduling and evidence controls" step.
- **The pristine head passes.** Only `yosys-elaboration` and the verdict differ from the template at the
  derivation, and a docs-only result set stays green when the real verdict script runs under bash.
- **17 planted defects in the generated graph are refused**, each in its own words:
  - a key bound to the workflow files;
  - a key without its version, source, recipe or image;
  - a tool-cache fallback;
  - a tool job without its build;
  - a timeout raised on the tool job, or on the consumer;
  - a tool job on another condition;
  - a consumer that builds, or lacks the need;
  - a restore that accepts a miss, has a fallback, or restores another key;
  - a verdict without the need, or without the pair. For these, the real verdict script runs with `yosys-tool`
    failed and `yosys-elaboration` skipped.
- **The key's inputs.** An edit outside the build recipe changes the generated workflow and leaves the key

- **Five template defects are refused by the generator:** a key without its one workflow-file digest, a missing

  pair.

## Known limitations / out of scope

- **`publication-census` is unchanged**, by assignment ("do not touch any other job's behaviour"). It still builds
  Yosys under its own workflow-bound key, so a workflow edit rebuilds it cold. That took 26 min 55 s of its
  45-minute timeout at `847eb4dd` (job 121450772909). Restoring from `yosys-tool` there is a candidate follow-up
  Issue.
- **A failed cache save fails closed.** If the tool job's cache save does not complete, `yosys-elaboration` refuses
  on the miss. Re-run all jobs; re-running only the failed one repeats the refusal.
- **The image in the key is the pinned label** `ubuntu-24.04` with `runner.os`, not the weekly image version. A
  binary built on one 24.04 image update is reused on the next, as before.
- **A recipe change is slower cold.** The rtl-fast critical path is then the tool job followed by
  `yosys-elaboration`, each inside its own 30 minutes. A workflow edit alone no longer causes a cold build.
- **First dev push after merge.** It misses the new key once on `dev`, because PR-scoped caches are invisible to
  `dev`. The cold build then runs in the tool job.
- **The act replay is slower.** act runs dependency stages in sequence, so the replay adds about one
  `yosys-elaboration` run to its wall clock, and builds the tool cold in each replay.
- **No RTL changed**, so no Verilator, Yosys or Vivado bank was run.
- **`ci/image/tool-inventory.json` is not regenerated.** It already records stale workflow digests at dev, and its
  `--check` belongs to the image build.
