**Scope (acceptance 1-4 in this repository).**
- One tracked machine-readable command table: opcode, command and response sizes, status set, hazard class, and lock and notify flags, per command the engine serves.
- `hdl/aecp/ucode/gen_ucode.py` takes its dispatch data from the table. The F06.14 doc table is generated from it. Where generation is not practical, a script in `scripts/` gates the hand-written form against the table, and the reason is recorded.
  - The engine's `OP_*_C` constants in `KL_aecp_engine.sv` are generated or gated too, in the manner of `check_upc_map.py`.
- The gate runs in CI. A drift in any consumer (ROM data, engine constant or doc row) fails by name.
- REQ-VER-002's Cov/Arch cells and 09 section 8 record what is generated and what is still hand-written.
- The generated ROMs and the elaborated engine are byte-identical at base and head. This lane changes where the data comes from, not what it is.
- Out of scope here: the Mark II firmware's AECP tables, which live in the parent. Name the export the parent will consume (format and path). Its parent gate is a follow-up lane after this merges.

**Proof.**
- Generated ROM digests are identical at base and head, and so are `syn/yosys/run.sh` and the processor suites. Records are identical.
- Planted drifts, each failing the gate by name:
  - an opcode renumbered in the table only;
  - a size changed in the doc table only;
  - an `OP_*_C` changed in the RTL only;
  - a command missing from the table.
- The scratch parent at dev `e8454e27`, with the gitlink at your head, passes its AECP and ROM-digest gates unchanged. The manager runs the donor and consumer banks.
